# Fusion 位深真实窗口验收

本阶段把 `1c7d1da` 的生产代码实际加载到主服务和 GT Studio 应用包，并完成位深控件、共享 MCP 状态及节点 PNG 的真实窗口检查。之前仅在独立服务中做过位深重放，不能据此声称当时的旧桌面会话已经加载新版。

## 加载与工程保护

更新前核对主服务工程与已保存演示工程一致；旧文件缺省声像按既有迁移规则解释为0。观察到 Media 页、第0帧暂停、近期桌面心跳且无待处理导航或活动渲染。只终止命令行、用户身份及监听端口均核对过的本项目旧界面/服务，等待进程退出后才加载新代码，不依据窗口读取超时判定进程已停止。服务更新会清空原内存撤销历史和任务列表。

新服务重开同一个 `GT Studio Fusion Desktop Demo.json`，恢复原页、帧和暂停请求。一次直接开发进程启动没有应用包注册身份，确认其退出后再通过 CUA 加载 GT Studio 应用包；随后窗口可正常读取并观察到有效预览。重启未修改保存文件，SHA256 保持 `5321c54669d13c3ef9662fa4e0b6919b3c4fbaf53b25dc13c5140d343a8bb027`。图标相关既有工作区改动没有纳入本阶段提交。

## 窗口、MCP 与输出

1. 用 MCP 切换到 Fusion，在真实界面选择演示片段，再点选 Blue overlay / Background 节点，观察到缺省 `Default (8-bit)`。
2. 用真实组合框和键盘选择 `16-bit integer`；确认 RGBA 仍为 `(0,0,1,0.5)` 后点击 **Apply node parameters**。主服务 MCP 读回 `Depth=2`，图中其余字段与原图相同。
3. 按既有配置启动一个新的 stdio MCP 会话，连接同一个主服务/工作区。它的更新参数目录包含 `Depth` 枚举 `[0,1,2,3,4]`，并在主服务写入 `Depth=4`；真实窗口随后回显 `32-bit float`。这个检查没有建立私有 Controller，不与之前的隔离服务重放混淆。
4. 从真实窗口点击 **Save selected node PNG…**，经系统保存对话框导出当前节点、第0帧；随后通过 MCP 对同一节点/帧再次导出。两文件均1233字节，逐字节相同，SHA256 为 `64da292639473f29e1d7799ab0cfdb8768af4e18d4c9a218906e87c7096e88cd`。完整320×180 RGBA16图像的每个像素均为 `[0,0,65535,32768]`。32位浮点是节点的计算精度，PNG检查点仍为16位通道。
5. 通过 MCP 两次撤销，分别核对回到 `Depth=2` 的窗口写回状态及原来省略 Depth 的图。真实窗口再次显示 `Default (8-bit)`。全工程与更新前一致，保存文件摘要不变；之后重开同一文件清理测试重做记录，恢复 Media 页、第0帧暂停，并观察桌面应用已响应。

本机旧 MCP 会话的工具目录仍可能缓存更新前的参数模式；新的已配置 stdio 会话已验证新参数可用。主服务与应用窗口已更新，不需要把“重新启动 MCP 客户端以刷新目录”和“主服务尚未加载代码”混为一谈。

## 控件检查及范围

最初在桌面操作下拉框失败时曾怀疑后台刷新会关闭列表，但控件复测没有支持这一判断：不变状态轮询和另一个 MCP 标记编辑后，列表都保持展开，键盘选片段成功。没有据此修改生产刷新逻辑。`test_fusion_ui.py` 现在直接通过选择器选片段，并覆盖这两种刷新以及既有位深写回、外部回显、锁轨和导出行为；该项本机通过。

本地原始运行记录为 `fusion-image-precision-live-reload.json`、`fusion-depth-live-mcp-writeback.json`，PNG保存在工作区，机器路径和完整工程快照不发布。本文记录真实 GT Studio 窗口验收，不证明 Resolve 全部界面、节点算法、最终编码颜色或性能一致。原18个精度案例、15组最终RGB及其残差仍见 [FUSION-IMAGE-PRECISION.md](FUSION-IMAGE-PRECISION.md)。
