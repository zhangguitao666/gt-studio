# Fusion 图像位深与输入归一化

本次将 Background 的图像位深接入节点渲染、MCP 和 Qt 参数检查器。原先全部节点使用不量化的 float32，不能重现默认生成器的 8 位舍入。现在保持浮点运算载体，在需要的位置按节点精度量化。完整 Fusion、内部浮点缓冲区及最终编码颜色一致性仍未达到。

## 原版实验与证据边界

目标为本机 Resolve 21.1.1.10 免费版，仅使用专用 `REA Reference · 2026-10-21` 工程、自有素材及受控时间线。原版 Lua Utility 脚本在时间线标记中保存设置、节点读回和准确的渲染任务 ID；保存工程后使用 SQLite backup 获取一致性快照。提取器只依据同一解压记录内的标记字节、JSON 前缀及明确的实验字段选择记录，不推断私有数据库包装结构。创建任务成功与渲染完成分别检查。

先对四个既有静态合成分别导出 ProRes422HQ、ProRes4444/Alpha、FFV1 RGBA16 无 Alpha 和有 Alpha，共 16 个最终接受的任务。全部 Complete/100%，不再渲染，实际均为 640×360、24fps、48 帧。最初的无 Alpha 请求带有不接受的 Alpha 设置，第二轮 ProRes422 仍拒绝；第三轮去掉该编码器的两个 Alpha 字段才成功。拒绝记录保留，不计为成功。公开的 `probe_resolve_fusion_output_pairs_rgb.lua` 是第二轮历史请求，刻意保留拒绝条件；常规成对脚本已使用有效字段，已有标记的工程不能直接重复运行。

四组新 ProRes422 的完整 RGB 都与旧参考相同，证明旧参考并未过期。同组 FFV1 有无 Alpha 的 RGB 也完全相同，差异不能仅归因于 Alpha 导出开关。FFV1 RGBA16 是颜色与编码处理之后的载体，不是直接读取内部节点缓冲区。

另建 320×320、24fps、12 帧的五组生成器位深、七组 Merge 位深组合和两组默认位深舍入样本；14 个任务均 Complete/100%，且完整帧序列都是对应的恒定 RGBA16 值。连同四个既有图，共形成 18 个严格摘要基准。原版导出、数据库及程序文件不进入公共仓库；夹具保留自有实验参数、任务终态、文件和解码摘要。

REA CLI 用现有兼容 Node 24.22.1 检查离线快照结构及 `BtLockableBlob` 的一行主键，没有修改 MCP 配置或安装分析器。Merge 快照 SHA256 为 `bc416fd06bfbee953051f9770de6c37d4b60c900247b2265fe0103538c7caaf3`，Evidence 为 `ev_9d145cefc95364f71c617b5e2d9b03aec7b2ab7cd79fe12fb6f165946f74ea25`。新增舍入快照的 Evidence 为 `ev_6a67395063c2517be15f7487580a4d04188c645fa24e4f37573f444ed6ddd907`，快照摘要另列于夹具。REA 的结构检查不证明标记语义、DSP 或像素等效。

## 节点计算

`Background.parameters.Depth` 接受以下枚举；非枚举小数、布尔、字符串、非有限值及越界值整笔拒绝。

|值|独立模型行为|
|---|---|
|0|Default，在受控原版环境中观察为 8 位整数|
|1|8 位整数，限制到 0..1，按 255 量化|
|2|16 位整数，float32 缩放到 65535 后使用最近偶数舍入|
|3|16 位浮点，按观察到的向零截断精度量化|
|4|32 位浮点|

参数先转换到 float32。默认位深两组 RGBA 输入 `(0.1,0.3,0.5,0.7)` 和 `(0.9,0.49999,0.50001,0.9999)`，原版载体分别为 `[6682,19789,32896,45746]`、`[58853,32639,32896,65535]`；这支持随后使用双精度乘 255 并舍入的规则，不能扩展为所有 GPU 和所有半值的证明。

Transform 继承输入精度，相邻默认变换仍先合并再采样一次，随后量化结果。Merge 先将前景转换到背景精度，再执行关联 alpha-over，并量化到背景精度；不同位深前后景交换时结果可不同。默认位深在本模型固定为 8 位，尚未实现原版全局/合成偏好的继承。半精度的特殊值、次正规数和溢出边界尚无原版覆盖，当前实现不应被称为完整 half 运算器。

旧文件省略 Depth 时继续保留省略形式；只读目录、渲染、保存重开均不自动写入参数。新检查器从参数目录取得缺省值，以组合框显示五种精度，通过同一个更新动作写回。旧运行界面不会因后端给默认节点新增字段而读取未知参数。

## RGB8 输入

受控 QTRLE 的 Auto 跟随原版 Video 数据电平。显式 Video 或该 Auto 路径在 16/235 映射之前，先按 `code * 257` 将 RGB8 和 Alpha 独立扩展到 16 位，再归一化到 float32。直接 packed RGB8 转 planar/16 位会引入通道偏移；直接转换到浮点也可能错误映射 Alpha。现在先提取原始通道，分别转换，再合并。全 256 码值的 RGB 与 RGBA 斜坡测试覆盖整数精确扩展、浮点不超过 1 ULP 及 0/1 端点。

Full 和其他 Auto 保留单独测量的解码扩展。曾将精确 UNORM 路径应用到所有 RGB8，导致原本一致的 Full/Blend=0 红色从 249 变为 251；最终按数据电平语义限制后恢复。没有按夹具名称、路径或测试编号切换。15 组最终 RGB 对照从旧模型的10组增加为12组精确一致，Full/Blend=0.25及0.5也对齐；这并不证明 Full 内部 RGBA 缓冲区完全一致，尚需直接的受控载体实验。

首轮 Linux CI 在 FFmpeg 8.1.3 下出现18项失败、347项通过，具体错误为 `GREY color family cannot have RGB matrix coefficients`。`extractplanes` 的灰度输出可能保留 RGB 父图像的矩阵标签，新版 zimg 拒绝该组合；本机 FFmpeg 7.1 连显式 RGB 标签输入也未拒绝，不能声称已在本机复现这个版本差异。修正对各灰度通道显式指定相同的非 RGB 输入/输出矩阵，只进行全范围位深扩展；重组 RGB 后恢复 RGB 矩阵标签。RGB/RGBA 斜坡又加入有/无显式 RGB 标签的组合，比较标准仍是全部256码值精确扩展及原18组摘要，没有按操作系统切换路径。

## 验证与剩余差异

`tests/fixtures/fusion-image-precision.json` 保存 18 个原版基准。引擎检查在首帧、末帧对完整 RGBA16 图像计算 SHA256，并检查保存重开和渲染不改变工程/历史。`scripts/verify_fusion_image_precision.py --run-name NAME` 通过实际配置的 stdio MCP 重建相同场景、检查 Depth 枚举，再做相同首末帧比较。它使用独立工程，不覆盖桌面演示工程。

首轮本机363项及两组新增样本通过；Linux矩阵标签修正后，本机完整367项通过（210.34秒）。配置 MCP 再次重建18个案例的首末帧，共36幅整幅RGBA16摘要全部相同，15组最终RGB指标保持12组精确一致。Qt 检查包含 Depth 默认值、组合框更改经HTTP写回共享节点、外部参数回显和锁轨禁用，但本次原有 GT Studio 窗口的 CUA 获取仍超时，不能将 Qt 测试写作新版真实窗口验收。远程完整集合包含新增夹具，结果按本次修复提交的 GitHub Actions 核验。

六组旧 Fusion 输出重新通过 MCP 导出：背景、共享分支和恒等三组最终 RGB 精确一致，六组 PCM 全流相同。其余结果如下，指标针对全部 48 帧解码 RGB 通道：

|案例|本次 MAE|本次 MSE|
|---|---|---|
|Merge|0.0239482060|0.3628862847|
|90° 旋转|0.0663744213|1.9869357639|
|缩小变换|0.0394864005|1.0039308449|

上版缩小 MSE 为 1.001972，本次有小幅退化；没有隐藏或放宽比较。四个既有图的 RGBA16 检查点精确一致，也不能替代最终 ProRes422 RGB 的残差分析。通用 DoD/画布外存储、Merge 变换合并、Flatten、其他滤波器、关键帧、遮罩、完整色管和完整节点集仍开放。该阶段改善图像精度，并不完成全功能一致目标。
