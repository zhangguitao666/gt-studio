# RGB8 输入与 ProRes 输出转换

新增原版载体实验揭示：先前保留 Full 模式的旧解码扩展，虽然让部分最终 RGB 相同，却让节点检查点出现偏差。本次统一 RGB8 的 UNORM 归一化，并为关联合成时间线的 ProRes 输出显式执行 SMPTE170M、视频范围、10位 YUV 转换。普通 YUV 时间线不增加 RGB 往返转换，MP4 输出不套用该 ProRes 转换。任意项目色管、其他输出矩阵及 HDR 仍未实现。

## 新原版证据

仅在专用 REA 工程中重新导出四个既有源电平案例，保持源、节点和电平设置不变。Auto/Blend=1、Video/Blend=1、Full/Blend=0.5 与 Full/Blend=0.75 均采用 FFV1 RGBA16、有 Alpha，640×360、24fps、12帧。四个准确任务全部 Complete/100%，rendering=false，完整序列的尺寸、帧数和恒定像素均核对过。创建任务成功不作为完成证明。

|案例|原版完整序列恒定 RGBA16|旧独立检查点|
|---|---|---|
|Auto / 1|35173, 0, 63150, 65535|完全相同|
|Video / 1|35173, 0, 63150, 65535|完全相同|
|Full / 0.5|48510, 0, 32768, 65535|48322, 1, 32768, 65535|
|Full / 0.75|40382, 0, 49151, 65535|40226, 1, 49151, 65535|

Full/0.5 的旧最终 ProRes RGB 已经相同，但这张表仍发现载体差异，说明最终 RGB 一致不能替代节点阶段的检查。所有模式都先将8位码值按 `code*257` 扩展，再解释电平后，四组完整 RGBA16 首帧摘要全部相同。Video 的16/235映射保持在归一化之后；Full不做该映射。该改动按源像素格式实施，不按样本名、路径或操作系统切换。

这些是原版导出载体，经过颜色/编码处理，不是直接读取内部 float32 缓冲区。新的输入规则由源码值、受控参数和四组载体共同支持，不据此声称所有媒体和节点已等效。公共 `fusion-image-precision.json` 夹具增加这四组的参数、源格式、电平、任务终态和完整摘要，合计22组；RGB24来源与原先ARGB来源分别生成并逐帧验证。

保存标记从 SQLite backup 快照提取，仍只依据解压记录内的标记字节与明确实验字段选择，不推断私有包装结构。该快照SHA256为 `e02902734558646e12ede06b7cde21d7cb73904b8740e1b1e4663799a339efe5`。REA 用现有兼容 Node CLI 检查同一快照结构及一行主键，Evidence `ev_87c7aa165f50d5be9721e60279d53740ed624c8c5d69a7f0d45c5897fe7fdd9b`。它不证明DSP、标记语义或颜色算法。公开探针为 `probe_resolve_fusion_level_rgba.lua` 及其状态脚本；已有标记会拒绝重复运行，数据库与原版媒体不发布。

## 分开检验颜色转换与编码器

先从研究性的正确输入计划取出 Merge 浮点输出，分别转换成 YUV10，再把相同 YUV 载体交给 prores_ks 和已有 VideoToolbox 编码器。两种编码器在四个案例中给出相同 RGB。显式601转换使四组 RGB 都与原版相同，隐式swscale转换保留原来的偏差，因此没有为每个样本更换编码器。

|案例|原版 YUV10 中心|显式601载体 YUV10|两者解码 RGB|
|---|---|---|---|
|Auto / 1、Video / 1|301, 863, 682|301, 862, 682|134, 0, 243|
|Full / 0.5|308, 624, 807|308, 624, 807|186, 0, 126|
|Full / 0.75|300, 755, 733|300, 755, 734|154, 0, 188|

表中也保留了一个 YUV 码值的差别。RGB完全相同并不等于 YUV、ProRes比特流或原版编码器完全相同。709矩阵的研究对照在这些SD案例中有明显差异；它不构成其他分辨率应使用哪种矩阵的证明。当前显式601只校准已实现的无色管关联 ProRes 路径，完整输出色彩设置仍开放。

研究候选路径先重放15组完整电平序列，15组全部 RGB 相同；六组旧 Fusion 的背景、共享分支和恒等仍相同，六组 PCM 全流相同。三个几何案例的候选 MSE 分别从0.362886降至0.000140336（Merge）、从1.986936降至0.0000694444（旋转）、从1.003931降至0.000368924（缩小）。残差仍存在，没有把它们改名为精确一致。

## 检查范围

新增四个原版载体检查在修复前实际得到两项失败、两项通过，Full两项失败与上表一致。修复后四项均通过。原电平测试仅检查32×32项目中的中心像素、允许差4，且源为160×90、存在黑边；它不能证明原640×360完整图像一致。现在使用与原版相符的640×360 RGB24源、12帧区间，严格比较已有原版夹具的完整 RGB SHA256，覆盖全部15组，没有放宽阈值。

`verify_fusion_image_precision.py` 通过配置MCP重建22组并检查首末帧共44幅 RGBA16；`compare_fusion_media_levels.py` 保存测量报告后要求15组全序列RGB精确一致，失败即报错；六组旧几何/音频重放另行报告。整个软件的节点集、DoD、滤波、关键帧、完整色管、其他编解码器、性能和界面仍未等效。

生产入口的配置MCP重放已完成44/44幅RGBA16精确匹配、15/15组完整RGB精确匹配；六组旧输出RGB指标与研究候选相同，六组PCM全流相同。本机完整371项通过（556.55秒）；远程CI按本次提交核验。

## 跨解码器参考修正

`55bc4cb` 的 Linux 检查为356项通过、15项RGB摘要失败。原断言把Mac/FFmpeg 7.1解码取得的RGB摘要直接用于Linux/FFmpeg 8.1.3，未让两个导出经过相同解码路径，不能单凭它判定编码输出是否一致。本机诊断证实：同一个原版Full/0文件，默认CPU路径解码为 `[249,0,0]`，关闭SIMD后为 `[251,0,0]`，文件本身没有变化。

新的 `fusion-prores-reference.json` 保存自有纯色色板的去元数据视频参考：只流复制原ProRes编码包，不重编码像素、不含音频或用户素材。每个参考12个编码包的SHA256及顺序均与原MOV核对相同；重新解码还必须符合原采集环境中的既有RGB摘要。15个案例去重成10个参考，压缩JSON约25KB。原MOV文件摘要和原采集RGB摘要继续保留，没有重写成当前渲染器的结果。除这组最小自有测试参考外，原始导出文件、软件程序和数据库仍保存在本地。

现在用同一个实际FFmpeg后端分别解码原编码参考和独立输出，继续要求12帧的全部RGB字节完全相同，不增加像素容差，也不按操作系统选择结果。`capture_fusion_prores_reference.py` 可以从受文件摘要约束的原版测量清单重新采集到新文件，拒绝覆盖已有参考。本机15项配对检查通过。

诊断也看到Full/0.75在关闭SIMD时原版为 `[154,0,190]`、独立输出为 `[157,0,190]`。因此不能声称所有解码路径或原始YCbCr已经一致；上表的YCbCr差异与这一反例继续保留。新的配对检查报告实际默认后端下的结果，完整编码器和色彩算法等效仍未完成。

## Linux 完整图像诊断

`30f3242` 的配对参考检查仍为356项通过、15项失败（Actions 40615800080）。15组首像素均相同，但完整RGB字节不相同，因此不能把此前失败全部归因于跨环境参考摘要。此问题继续开放。

新增独立诊断任务重建 Auto/0 与 Full/0.75，记录首帧差异边界、首个差异像素、颜色计数、每帧摘要和YUV10各平面码值。该任务成功仅表示诊断执行完成，不代表图像一致；完整371项测试仍单独执行，断言和阈值保持不变。两个任务使用同一个固定版本、固定SHA256的FFmpeg；安装脚本从原工作流原样提取，语法树核对一致。

本机诊断两组RGB均完全相同；Auto/0的YUV也相同，Full/0.75的原版Cr为733、独立输出为734。Linux结果需要另行核对，不由Mac结果推断。

Actions 40617886910 的独立诊断执行完成。Auto/0差异边界为x=320..639、y=352..359，首个差异位于(326,352)，原版[253,0,0]、输出[253,0,1]；输出另有318个纯黑像素。Full/0.75差异也局限在右下角，含318个纯黑像素。两组12帧均不同；原版YUV平面为恒定值，输出Y平面各有320个码值64。它证明存在空间边缘异常，不能用首像素一致替代完整图像一致。
